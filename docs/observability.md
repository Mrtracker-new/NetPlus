# NetPulse Observability & Structured Logging Standards

This document establishes the observability architecture, logging policies, event taxonomy, field conventions, and privacy guarantees across all NetPulse crates and binary services.

---

## 1. Core Goals & Architecture

1. **Structured & Auditable**: All logs are emitted as structured key-value events using `tracing`. Raw `println!` / `eprintln!` calls are forbidden in binary services and libraries.
2. **Zero Overhead Hot-Loops**: Packet decoding and flow ingestion hot-loops omit per-packet logging by default. Detailed packet trace logging is explicitly feature-gated under `trace-packets`.
3. **Strict Privacy Policy**: Network packet payloads, raw binary traffic buffers, user credentials, secrets, and API keys are **never** logged. Functions processing raw buffers must use explicit field skipping (e.g. `#[instrument(skip(bytes), fields(bytes_processed = bytes.len()))]`).
4. **OpenTelemetry / Aggregator Ready**: Subscribers are composed via `tracing_subscriber::registry()` with layered `EnvFilter` and formatting layers. Adding OTLP exporters or metrics backends in the future requires zero changes to application instrumentation code.

---

## 2. Telemetry Configuration & Initialization

Initialization is driven by `netpulse_core::telemetry::TelemetryConfig` and helper functions:

```rust
use netpulse_core::telemetry::{init_telemetry, read_env_config};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = read_env_config("netpulse-engine", env!("CARGO_PKG_VERSION"));
    let _handle = init_telemetry(config)?;

    let root_span = tracing::info_span!(
        "engine_root",
        service = "netpulse-engine",
        version = env!("CARGO_PKG_VERSION"),
        pid = std::process::id()
    );
    let _entered = root_span.enter();

    tracing::info!(event = "engine.start", "NetPulse engine started");
    Ok(())
}
```

### Environment Variables
- `RUST_LOG`: Controls filter directives (e.g. `RUST_LOG=info`, `RUST_LOG=netpulse_engine=debug,info`). If unset, defaults to `debug` in debug builds (`cfg!(debug_assertions)`) and `info` in release builds. Invalid filter values automatically fall back safely.
- `RUST_LOG_FORMAT`: Selects output format (`full`, `compact`, or `json`). Default is human-readable compact text.

## 3. Log Levels Policy

| Level | Usage | Examples |
| :--- | :--- | :--- |
| `ERROR` | Unrecoverable failures or actionable operational errors logged at boundary entry points. | Database open failure, capture service launch crash, invalid IPC payload. |
| `WARN` | Recoverable anomalies, degraded operation, or fallback behavior. | Missing host name hint, packet shed threshold reached, frame decode fallback. |
| `INFO` | Major application lifecycle milestones and aggregated summary reports. | Engine boot/shutdown, capture started/stopped, PCAP analysis completed. |
| `DEBUG` | Pipeline stage details, state transitions, query execution. | Batch reconstruction completed, correlation lookup performed, query served. |
| `TRACE` | Verbose per-item tracing (strictly feature-gated or explicit debug filter). | Individual flow state mutation, frame header parse detail. |

## 4. Event Taxonomy & Standardized Fields

### Event Taxonomy
Use standardized `event` field strings for major system events:
- `engine.start` / `engine.shutdown`
- `capture.started` / `capture.stopped`
- `pipeline.analysis_started` / `pipeline.analysis_completed`
- `storage.write_completed` / `storage.prune_completed`
- `system.panic`

### Standardized `snake_case` Metric Fields
All numeric metrics and correlation identifiers use consistent `snake_case`:
- `analysis_id`: Unique identifier for an offline analysis execution.
- `capture_id`: Unique identifier for a live capture session.
- `flow_id`: Engine flow identifier.
- `session_id`: Reconstructed session identifier.
- `frames_read`: Total raw frames ingested.
- `packets_decoded`: Count of successfully decoded frames.
- `flows_created`: Count of flows constructed.
- `sessions_created`: Count of sessions assembled.
- `analysis_ms`: Monotonic elapsed time in milliseconds for analysis pipeline execution.
- `storage_write_ms`: Monotonic elapsed time in milliseconds for storage persistence.
- `rebuild_ms`: Monotonic elapsed time for live store reconstruction.
- `bytes_processed`: Byte count of processed pcap or frame buffers.

---

## 5. Correlation ID Lifecycle & Propagation

1. **`analysis_id`**: Generated when `analyze_pcap` or `analyze_frames` begins. Recorded on the pipeline root span and inherited by downstream flow and session construction spans.
2. **`capture_id`**: Generated when `start_capture` is invoked in the desktop shell or capture service. Inherited by all `live_loop` reconstruction iterations.
3. **`flow_id` & `session_id`**: Generated by `netpulse-flow` and `netpulse-narrative` during packet processing and attached to sub-spans and query responses.

---

## 6. Panic Handling

`init_telemetry` automatically registers a panic hook that logs structured `tracing::error!(panic = %info, location = ..., event = "system.panic")` while preserving Rust's standard terminal panic backtrace formatting.

## 7. Health, Readiness & Liveness Probe Architecture

NetPulse binaries support three distinct operational probes served via HTTP (`httparse`) when enabled via `NETPULSE_HEALTH_ENABLED=true` or `NETPULSE_HEALTH_PORT=9876`:

1. **`/live` (Liveness Probe)**: Returns HTTP 200 `LivenessStatus` (`{"schema_version":1,"status":"alive"}`). Indicates process thread is alive; **never** performs I/O or blocks on mutexes.
2. **`/ready` (Readiness Probe)**: Returns HTTP 200 (Ready/Degraded) or HTTP 503 (Unhealthy) `ReadinessStatus` with explicit component checks (`storage`, `capture`, `telemetry`, `workers`).
3. **`/health` (Full Operational Health Probe)**: Returns HTTP 200 (or HTTP 503) `HealthSnapshot` with process uptime, active flow/session metrics, memory indicators, build metadata, and component checks.

### Evaluation Policy
- **Healthy**: All `Required` components are healthy.
- **Degraded**: All `Required` components are healthy, but one or more `Optional` components (e.g. idle capture backend) are degraded.
- **Unhealthy**: One or more `Required` components (e.g. storage or worker threads) are unhealthy.

### Time Budget Contract & Non-Blocking Design
All `HealthProvider` implementations **must complete instantly without blocking I/O or locking mutexes**. Probe metrics are backed by lock-free atomic variables (`AtomicHealthTracker` using `AtomicBool`, `AtomicU64`, `AtomicUsize`).
